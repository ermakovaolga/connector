# Архитектура и заметки PoC

Локальный PoC: **TUN → policy routing → FortiClient**. Без Liberator и без сервера.
Пользовательская документация лежит в [README](../README.md).

```
приложение (curl d.dgx:18888)
   │  DNS *.dgx  ──/etc/resolver/dgx──►  агент (198.18.0.2)
   │                                       │ спрашивает 10.32.1.3 сокетом, привязанным к utun FortiClient
   │                                       │ отвечает fake IP 198.18.1.x  (помнит: d.dgx → 10.32.2.11, outbound=itmo)
   ▼
198.18.1.x ──маршрут 198.18/16──► utunN агента ──► gVisor netstack (TCP/UDP терминируются в userspace)
                                                     │ policy: fake IP → itmo | ip_cidr → itmo | иначе → direct
                                                     ▼
                                   новый сокет с IP_BOUND_IF = utun FortiClient ──► ITMO
```

Главные свойства:

- **Маршруты FortiClient не трогаются.** Агент добавляет только `198.18.0.0/16` в свой TUN и
  `/etc/resolver/dgx`. FortiClient известен тем, что следит за таблицей маршрутизации.
- **Номер utun не зашит.** Интерфейс ITMO ищется по самому специфичному маршруту до `10.32.1.3`
  (маршруты `default`, `0/1` и `128/1` игнорируются). Если FortiClient не подключён, агент выдаёт
  ошибку и не отправляет трафик ITMO в чужой VPN.
- **Transit нет.** Для FortiClient все соединения исходят от самого Mac, поэтому вопрос
  «разрешает ли FortiClient форвардинг» на этом этапе не возникает.
- **Кроссплатформенность.** Один код на Go, отличается только слой `sys_*.go`
  (macOS: `ifconfig`/`route`/`/etc/resolver`; Windows: wintun/`netsh`/NRPT).

## Сборка

```bash
go build -o vpnpoc .                                   # macOS
GOOS=windows GOARCH=amd64 go build -o vpnpoc.exe .     # Windows (+ wintun.dll рядом)
```

## Эксперименты

### 0. `probe`: механизм без root и без TUN

```bash
./vpnpoc probe                    # цели ITMO по умолчанию
./vpnpoc probe 10.32.0.3:80 10.32.15.89:443
```

Для каждой цели выводит: какой outbound выбрала политика, результат TCP connect через сокет,
привязанный к этому интерфейсу, и **негативный контроль** (тот же connect через другой outbound).
`REFUSED` — хост достижим, порт закрыт; `TIMEOUT` — пакеты не проходят или отбрасываются.

### 1. Self-test (ITMO не нужен)

```bash
sudo ./vpnpoc run -c config.selftest.yaml     # терминал 1
./test.sh example.com https                   # терминал 2
```

`example.com` уводится в `en0` в обход активного full-tunnel VPN. Это та же механика,
которая нужна для ITMO.

### 2. Основной тест: ITMO

1. Подключить FortiClient ITMO.
2. `./vpnpoc probe`: у `itmo` должен определиться `utunN`, `10.32.2.11:18888` должен дать CONNECTED.
3. `sudo ./vpnpoc run`
4. `./test.sh`: ожидается `d.dgx → 198.18.1.x → utun агента → HTTP 200`, а в логе агента
   строка `tcp 198.18.1.x:18888 (d.dgx -> 10.32.2.11) -> itmo[utunN] connected`.

### 3. Опционально: обращения по IP (`capture_ip_rules: true`)

Маршруты `10.32.x/32` уводятся в TUN агента. Проверяет, как FortiClient реагирует на
пересекающиеся маршруты. Чтобы привязанный сокет агента не зациклился в собственный TUN,
агент дублирует каждый такой маршрут scoped-маршрутом (`-ifscope utunN`) на интерфейс FortiClient.

## Найдено по ходу (macOS)

Сокет с `IP_BOUND_IF=X` получает маршрут, только если самый специфичный маршрут ведёт в X
или для X есть scoped-маршрут. Когда full-tunnel VPN держит `0/1 + 128/1`, у `en0` нет
scoped default, и привязанные к `en0` TCP-сокеты получают `network is unreachable`
(`curl --interface en0` ломается так же). `run` добавляет `route add -ifscope en0 default <gw>`
и удаляет его при выходе. Для FortiClient это не проблема: его маршруты `10.32.x` и так самые
специфичные.

### Конфликт двух VPN: шлюз ITMO уходит в чужой туннель

Лог FortiClient (`/Library/Application Support/Fortinet/FortiClient/Logs/vpn-provider.log`) за 26.09:
туннель поднят в 00:30:11, а в 00:33:54 внешнее TLS-соединение упало с `read packet: Operation timed out` → `ioFailed`.
Одновременно full-tunnel VPN переподключился (`utun9`, `0/1 + 128/1`), и `route get 77.234.220.42`
стал вести в `utun9`: внешнее соединение FortiClient оказалось внутри чужого туннеля.
Поэтому в конфиге есть `bypass: [77.234.220.42/32]`: host-маршрут до шлюза ITMO через физический
default gateway, который не зависит от того, какой VPN держит `0/1`.

Защита от двойного запуска: если `198.18.0.0/16` уже маршрутизируется в другой TUN, агент не стартует.

## Служба и значок в меню

```
VPN Policy.app (пользователь) ──HTTP 127.0.0.1:47391──► vpnpoc daemon (root, launchd)
      GET /status, POST /on, POST /off                     Agent.Start / Agent.Stop
```

- Служба (`/Library/LaunchDaemons/local.vpn-policy-poc.plist`) работает всегда. Кнопка только
  включает и выключает перехват, поэтому пароль нужен один раз, при установке.
- API слушает только `127.0.0.1` и требует заголовок `X-VPNPoC: 1`. Браузер не может отправить его
  с чужой страницы без CORS-preflight, а preflight мы не разрешаем. Поэтому сайт не может выключить агента.
- Состояние вкл/выкл хранится в `/usr/local/vpnpoc/state` и переживает перезагрузку.
- Если старт не удался (например, сеть ещё не поднялась), служба повторяет попытку каждые 10 с.
- При смене сети (меняется физический шлюз) служба пересобирает маршруты `bypass` и scoped default.
- При запуске служба убирает следы аварийной остановки (`/etc/resolver/*` с маркером агента).

## Выход в VPN для адресов вне его маршрутов (`scoped_default`)

У outbound можно включить `scoped_default: true`. Тогда агент ставит `route add -ifscope utunN default`
на интерфейс VPN, и привязанные сокеты агента могут отправлять в этот VPN любые адреса, а не только те,
на которые VPN выдал маршруты. Остальной трафик системы этот маршрут не видит.
Пропустит ли такой трафик сам шлюз VPN, решают его правила. Например, `tatneft.guru`
(`31.41.241.159`) через шлюз ITMO не проходит (TCP timeout, проверено 30.09), поэтому правило для него выключено.

## Остановка

- Служба: кнопка «Выключить» в меню или `sudo launchctl bootout system/local.vpn-policy-poc`.
- Ручной запуск: Ctrl+C или закрытие окна терминала (обрабатывается SIGHUP).

В обоих случаях агент удаляет свои маршруты и `/etc/resolver/<suffix>` и сбрасывает DNS-кеш. TUN
исчезает вместе с процессом. Если агент убит через `kill -9`, следующий запуск уберёт остатки сам.
Убрать их вручную можно так: `sudo rm /etc/resolver/dgx`.

## Ограничения PoC

Только IPv4; AAAA → пустой ответ. ICMP (ping) до fake IP не форвардится. Пул fake IP живёт
в памяти: после перезапуска агента старые fake IP из DNS-кеша не работают
(TTL 10 с, и при старте кеш сбрасывается). Windows-слой компилируется, но на реальной машине не проверялся.
